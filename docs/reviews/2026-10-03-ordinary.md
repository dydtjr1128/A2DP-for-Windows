## Findings

### P2-1. 연결된 Idle 상태에서 "다음 stream 설정 준비"에 필요한 fresh capability를 얻을 길이 없음
- **근거**
  - `docs/interfaces.md:81`: ApplyPolicy에는 "ProjectDriver와 fresh capability 필요"하다고 되어 있습니다.
  - `docs/device-status.md:25`: link 연결·stream 대기 상태에서 "fresh capability"로 다음 stream을 준비할 수 있다고 합니다.
  - 그런데 capability 조회는 render demand로 들어가는 `Discovering`에서만 일어납니다 (`docs/interfaces.md:36`, `docs/architecture.md:108-111`).
  - 조회만을 위해 AVDTP 채널을 여는 것도 금지되어 있습니다 (`docs/device-status.md:29`, `docs/architecture.md:45`).
  - 캐시는 적용 근거가 될 수 없습니다 (`docs/device-status.md:37`).
- **실패 시나리오**
  - 재생이 없는 상태에서 "설정 적용"을 누르면 ApplyPolicy가 항상 CapabilityUnknown으로 실패합니다.
  - 또는 구현자가 금지된 캐시나 이전 세션 값으로 검증하게 됩니다.
  - 그러면 `ui-design.md:138`, `:148`의 "다음 재생에 적용할 설정 준비됨"은 도달할 수 없거나 계약을 위반한 상태가 됩니다.
- **최소 수정안**
  - Idle 준비 결과를 "local 검증만 통과, remote는 다음 Discovering에서 확인"으로 정의합니다.
  - 그 경우 ApplyPolicy의 fresh capability 요건은 Streaming과 Open 상태에만 적용합니다.
  - 다음 Discovering에서 불일치가 나왔을 때의 결과(NoCommonCodec 보고, fallback 여부)를 해당 표에 명시합니다.

### P2-2. 생명주기 상태도에 재생 중 재구성과 resume 전이가 없음
- **근거**
  - `docs/interfaces.md:59`는 설정 변경 시 "suspend → reconfigure 또는 media stream 재시작"을 계약으로 둡니다.
  - 그러나 상태도 `docs/interfaces.md:40-46`에서 `Suspended`의 출구는 `Discovering`(새 generation)과 `Stopping`뿐입니다.
  - `Suspended→Configuring/Open`, `Suspended→Streaming`(resume), `Streaming→Configuring` 전이도 없습니다.
- **실패 시나리오**
  - Streaming 중 ApplyPolicy를 처리하려면 상태도에 없는 전이를 만들거나, 매번 새 generation으로 Discovering을 다시 거쳐야 합니다.
  - 후자는 capability를 다시 조회하고 snapshot을 무효화하며 중단 시간을 늘립니다.
  - reconfigure가 `session generation`을 올리는지 `format_revision`만 올리는지 정의되어 있지 않습니다.
  - 그래서 `device-status.md:56`, `:77`의 window 폐기 기준과 `ui-design.md:156`의 늦은 결과 폐기 기준이 구현마다 달라집니다.
  - `ui-design.md:149`는 `Configuring`을 "설정 적용 중, 같은 request"로 표시합니다. 하지만 이 상태에는 UI 요청 없이 render demand로도 들어가므로 request 연계가 성립하지 않습니다.
- **최소 수정안**
  - Streaming→(suspend)→Open→Configuring→Open→Streaming 경로와 resume 전이를 추가합니다.
  - "reconfigure = 같은 generation, format_revision+1" 같은 revision 규칙을 표 하나로 고정합니다.

### P2-3. OS endpoint PCM 형식과 encoder 입력/codec sample rate의 소유권 경계가 정의되지 않음
- **근거**
  - `docs/architecture.md:53`: 첫 endpoint 형식은 48 kHz/16-bit/stereo이고 "숨은 resampling 없음", "다르면 명시적 변환 단계 필요"라고 되어 있습니다.
  - 반면 장치별 desired 설정에는 sample rate와 PCM sample kind/valid/container bits가 들어 있습니다 (`docs/interfaces.md:90`, `docs/ui-design.md:111-112`).
  - UI 예시에도 44.1/96 kHz, 24-bit, 32-bit float가 나옵니다.
- **실패 시나리오**
  - 사용자가 44.1 kHz나 24-bit를 저장하고 적용합니다.
  - 이를 만족하려면 Windows endpoint의 장치 형식을 바꾸거나(모든 재생 앱의 stream에 영향), 금지된 변환을 넣어야 합니다.
  - 문서는 둘 중 어느 쪽인지, 누가 소유하는지, Streaming 중 영향이 무엇인지 말하지 않습니다.
  - `device-status.md:35`의 "PCM 경로" 조건이 현재 Windows 장치 형식인지, driver가 광고할 수 있는 형식 집합인지도 모호합니다.
- **최소 수정안**
  - 입력 PCM 해상도와 sample rate를 둘 중 하나로 정합니다.
    - (a) 현재 endpoint 형식에서 파생되는 읽기 전용 값, 또는
    - (b) service가 driver 광고 형식을 바꾸는 명시적 동작. 이 경우 endpoint 재협상과 모든 client 영향을 사전에 안내합니다.
  - 정한 쪽을 `device-status.md` §2 권한 표와 `interfaces.md:90`에 반영합니다.
  - M2 전까지는 해당 control을 읽기 전용으로 둔다고 적습니다.

### P3-1. "다음 후보 시도" 계약과 `select_codec` 시그니처가 맞지 않음
- **근거**
  - `docs/interfaces.md:17`은 상세 협상이 실패하거나 peer가 거절하면 다음 후보를 시도한다고 합니다.
  - 하지만 `crates/a2dp-core/src/codec.rs:129-155`는 후보를 하나만 반환하고, 실패한 후보를 제외하는 입력이 없습니다.
- **실패 시나리오**
  - 실패한 codec을 `preferred`에서 빼는 방식으로 재시도한다고 가정합니다.
  - `[Sbc]`만 선호했다면 `EmptyPreference`가 되어 설정 오류로 잘못 분류됩니다 (`codec.rs:135`).
  - 명시적으로 선호했던 SBC가 PeerRejected된 뒤 나머지 선호도 실패하면, `AllowSbc` 아래에서 거절된 SBC가 `SbcFallback` 사유로 다시 선택됩니다 (`codec.rs:148`).
  - 이는 `interfaces.md:132`의 "같은 설정 무한 반복 금지" 및 사유 정확성과 충돌합니다.
  - 테스트(`codec_policy.rs`)에는 재시도나 제외 경로가 없습니다.
- **최소 수정안**
  - 재시도할 때는 실패한 codec을 `local_encoders`와 `remote_codecs`에서 제외한다고 문서화합니다.
  - 또는 `excluded: &[Codec]` 인자를 추가합니다.
  - 위 두 시나리오를 테스트로 추가합니다.

### P3-2. "선호 codec"이 단일 값인지 순서 목록인지 정의되지 않음
- **근거**
  - `docs/interfaces.md:11`은 선호 codec을 "순서대로 제공된 목록"으로 정의합니다.
  - `docs/interfaces.md:90`은 "codec preference"라고만 씁니다.
  - UI는 단일 드롭다운입니다 (`docs/ui-design.md:109`, 시안 이미지).
- **실패 시나리오**
  - UI 저장값(단일 codec)과 서비스 schema(목록)가 서로 다른 형태로 고정될 수 있습니다.
  - 2순위 선호를 표현할 방법이 없어 strict 실패 아니면 SBC fallback만 남습니다.
- **최소 수정안**
  - desired schema를 `Vec<Codec>`(길이 1 이상)으로 명시합니다.
  - UI는 길이 1 목록으로 시작한다고 적습니다.

### P3-3. SBC Mono 모드와 PCM 채널 수 계약이 빠짐
- **근거**
  - `docs/device-status.md:89`와 `docs/ui-design.md:110`은 SBC Mono를 선택지로 둡니다.
  - `docs/ui-design.md:119`는 PCM 채널 수를 "별도 field로 검증"한다고 합니다.
  - 그런데 `docs/interfaces.md:90`의 desired field 목록에는 PCM 채널 수가 없습니다.
  - `docs/architecture.md:53`은 숨은 변환을 금지합니다.
- **실패 시나리오**
  - stereo endpoint에서 Mono를 선택하면 downmix 단계가 없어서 거절되거나 정의되지 않은 동작이 됩니다.
- **최소 수정안**
  - 명시적 downmix 단계가 정의되기 전에는, PCM 경로와 맞지 않는 Mono를 사유와 함께 비활성으로 둔다고 명시합니다.

### P3-4. kbps 계산의 시간 기준이 driver counter와 묶여 있지 않음
- **근거**
  - `docs/device-status.md:72`, `:76`은 실제 elapsed monotonic time을 요구합니다.
  - 하지만 `docs/interfaces.md:106`의 `ReadCounters`에는 counter를 읽은 시각 필드가 없습니다.
- **실패 시나리오**
  - service가 IOCTL 반환 후 시각을 찍으면 IPC/스케줄링 지연이 1초 window에 섞입니다.
  - 그 결과 관측 kbps가 흔들립니다.
- **최소 수정안**
  - `ReadCounters` 결과에 counter와 같은 시점에 찍은 monotonic timestamp(QPC 등)를 추가합니다.

### P3-5. stale 경계 표현이 서로 다름
- `docs/device-status.md:78`은 "3초 이상", `docs/ui-design.md:216`(UX-15)은 "3초 초과"라고 씁니다.
- 경계값 테스트의 기대값이 둘로 갈립니다.
- 한쪽으로 통일하면 됩니다.

## 잔여 위험 / 검증 한계
- 문서 간 정합성만 정적으로 보았습니다. UI 동작, provider, telemetry, Windows endpoint 형식 동작은 확인하지 않았습니다. 특히 P2-3의 endpoint 형식 변경이 다른 앱에 미치는 영향은 미확인 추정입니다.
- `docs/adr/0001-rust-and-windows-boundary.md`, `docs/codec-and-distribution.md`(키워드 검색만, 일치 없음), `README.md`, `docs/sources.md`는 읽지 않았거나 일부만 보았습니다. 이 파일들에 위 항목과 상충하는 문구가 있는지는 남은 공백입니다.
- 테스트 공백: `codec_policy.rs`에 재시도·제외 시나리오(P3-1)가 없습니다. Idle 준비 결과와 이후 Discovering 불일치(P2-1)를 검증할 수용 기준도 UX-01~16에 없습니다.
